# 对话搜索（⌘F）引擎

> `lib/client.js` 里的搜索实现：三段纯函数（core / match / snippet）+ 一层接线。
> 回归测试：`npm run test:search`（`tools/search-engine.test.mjs`，直接从 `client.js` 抽取引擎，不是复制品）。
> 排布与编号的产品结论见 `docs/search-result-order-research.md`。

## 1 流水线

```
extract    每轮：user bubble = prompt 字段；每个非空 assistant step = 一个 step 字段
           （工具输出、报错文本都在 step 里，只索引最后一个回答会漏掉它们）
normalize  normalizeSearchText：NFKC → 去零宽 → 非 locale 小写 → 空白折叠
parse      parseQuery：裸词 / "短语" / -排除 → Plan{positives, negatives, canonicalKey}
match      从当前阅读轮次向外交替扫描，matchFields 判定整轮是否命中
count      继续走完，得到精确总数（选中的 50 条之外不再建行）
render     对选中的轮次做 buildSnippet（最密窗口），按文档序交给列表
publish    行数变化时发布；精确总数只在 settled 时落地
```

## 2 查询语法

| 输入 | 含义 |
|---|---|
| `预览 卡` | 两个词，AND；各自可命中同一轮的**不同字段** |
| `"预览卡高度"` | 精确短语，必须落在**同一个字段**内 |
| `-发灰` | 排除：任一字命中即整轮排除 |
| `-"foo bar"` | 排除短语 |
| `\"` `\\` | 引号内转义；未闭合引号当作"到结尾为止的短语"，不报错 |
| 裸 `-` | 字面量 `-` |
| 纯 CJK 串（≥3 码点） | CJK 子句：先精确匹配，再走有界容错（见 §3.2） |
| `React中文` | 混合脚本不拆分，整词按字面量匹配 |

## 3 匹配语义

### 3.1 字段与整轮

- 正向子句 **AND**；每条子句可以由该轮的任意字段满足。
- 短语与 CJK 子句**不得跨字段**（字段永不拼接，否则会凭空造出短语）。
- 任意排除子句命中任意字段 → 整轮排除。
- 一轮最多产出一行；`capped ⟺ 命中总数 > 50`。

### 3.2 CJK 容错

纯 CJK 查询长度 L（码点）：

1. 先按精确子串找；找到就用（最快路径）。
2. 否则允许**有界子序列**：查询的码点按序出现，跳过 ≤2 个码点，覆盖跨度 ≤ L+2。
   于是 `预览卡高度` 能命中 `预览卡的高度`（跳 1）与 `预览卡的两高度`（跳 2），
   但命中不了 `预览卡的两个高度`（跳 3）或 `览卡预览高度`（顺序错）。
3. 每子句最多 64 个 span；每个 gram 的位置收集也有上限（病态字段不会爆内存）。

## 4 排序、定位与计数

- 扫描从**当前阅读轮次**向外扩（旧一条、新一条交替），因此"最先命中的 50 条"就是**最近 50 条**。
- 显示恒按 `n` 升序（= 文档序），编号从小到大；锚点行放在列表顶部下方 22px，上一条只露半行。
- `matchTotal` 是精确总数，与 `settled` 一起发布；footer 显示 `共 N 条命中 · 显示最近 50`，
  另有 `role="status"` 的播报（只在 settled 时说话）。
- 点击跳转先按 `chatFlowKey`，找不到时按行携带的 `n` 兜底（revalidate 重编号后仍能命中）。

## 5 预算与阈值

| 阶段 | 预算 |
|---|---|
| 索引构建 | 每片 ≤2ms / ≤32Ki 字符；一个 step 一个子片（单个巨型 step 不会撑爆一帧）；`buildSeq` 世代守卫 |
| 扫描 | 每片 ≤4ms；匹配与建行**交替**推进，一个预算点最多建一行（200KB 字段单行可达 5–8ms） |
| 发布 | 仅在行数变化时发布；精确总数只在 settled 前最后一次落地 |
| 输入 | 60ms 防抖；IME 组合期间不发起搜索，`compositionend` 提交一次 |
| 生命周期 | 面板关闭后索引保留 5 分钟；过期/销毁时释放 `entries`、`build.turns`、`build.stepsArr`、`build.host` |

## 6 展示文本 vs 搜索文本

每个字段存两份文本：

- `text` —— **展示**用：NFKC、去零宽、空白折叠，但**保留大小写**。零宽字符必须去掉，否则它会挤歪所有偏移。
- `norm` —— **匹配**用：`text` 的小写形式（长度不变，因此 `norm` 里的 span 可以原样落在 `text` 上，高亮位置精确）。

`text` 与 `norm` 只在大小写上不同——如果两者折叠规则不一致（例如只对搜索侧做 NFKC），span 就会落在错误字符上，行内高亮整体消失。
土耳其语 `İ` 这类会改变长度的小写转换是唯一例外，此时 `fieldSnippet` 退化为无高亮的纯预览，而不是标错字符。

## 7 失效检测（`sameSnippet`）

索引里存的是归一化文本，轨道给的是原始大小写的 160 字符片段。**两侧必须做同一套归一化再比前缀**——
早期版本只归一化索引侧，导致任何带大写的轮次永远"脏"，`finish → revalidate → 整建` 自我循环。

已知边界（刻意接受）：

- 只比对前 ~160 字符：更靠后的编辑要等 keepalive 重建才发现。
- NFKC 组合跨越第 160 字符边界时可能误判为脏（失败方向是"多重建一次"，不会跳错轮次）。

## 8 已知限制 / 下一步

1. **倒排索引**：目前每次按键对全文 `indexOf`（切片执行，不卡但延迟随会话线性增长）。>400KB 时建 gram→轮次 postings 可把扫描变成集合求交。
2. **到 50 条就停**：现在为了精确总数会走完全部轮次；不想要精确总数时可省掉一半工作量（显示 `50+`）。
3. **last-step-first**：匹配字段时优先最新的 assistant step（聊天里命中率最高）。
4. **按 `canonicalKey` 复用结果**：同一查询在打开/revalidate 后无需重扫。

## 9 决策记录（暂不实现）

搜索结果以**一轮为一行**就是最终粒度，暂不引入出现级（同一轮内第 k 处）导航。相关结论留档，将来要做时不必重新讨论：

- 出现级步进方案已定：`↵` 跳到当前处并前进一处、`⇧↵` 后退；一轮走完继续进下一轮；命中处用绝对定位遮罩绘制（不改宿主 DOM，避免被 React 重渲染冲掉），偏移靠 `field.text` 与 DOM 文本节点的逐字符映射还原。难点只在映射（NFKC 会改变长度），引擎侧 span 数据已经现成。
- 不采纳：`← →` 步进（与搜索框光标冲突）、`#N` 轮次过滤语法、结果列表右缘密度条、`⌥↑↓` 跳档。理由：轮次级定位已由轨道（rail）承担，搜索浮层保持"选中一轮即跳过去"的最小模型。
